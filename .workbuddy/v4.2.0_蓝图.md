## 1. 目标定义（阈值预算模型）

**核心不是「把图压小」，是「预压到刚好卡在平台压缩阈值线下 → 平台判定已够小 → 不二次压缩 → 你的高画质版存活」。**

平台压缩有两道独立闸门，必须同时卡在线下：
1. **分辨率闸门**：长边超过平台上限 → 平台粗暴降采样（丢细节、引入模糊）。
2. **体积闸门**：文件超过平台体积安全线 → 平台二次重压（质量点暴跌 5–10+，暗部/渐变先遭殃）。

在双闸门线下，把**感知画质（色彩保真 + 细节保留）堆到预算内最高**。等价于 Guetzli 式「固定字节预算 + 自适应感知量化表」注入 JPG——不转 AVIF/HEIC（双次有损），直接在 JPG 自己的量化表里换「智能大脑」。

**为什么有效**：微信/小红书/IG 的二压质量点约 60–85 且优先干掉暗部。若我们本地用 Q≥80 预压到体积线内，平台拿到后「已够小」→ 跳过二压（或仅极轻处理）→ 我们预压的高画质完整保留。Ins 的「又小又清楚」正是此原理。

**跨平台共识（工程铁律，来自 Zipic 2026 实测对照表）**：
- 本地 JPEG Q 必须 ≥80（平台二压吞 5–10 点，本地要留余地）。

- 去 EXIF 元数据 + 修正 EXIF 方向（部分安卓客户端方向标记显示错）。
- **JPG 通吃**；WebP 仅 X/Reddit 接受，IG/FB 不优先返回 WebP → 社交平台统一 JPG。
- 体积比分辨率更致命：超体积线触发二压，分辨率达标但体积超标仍糊。

## 3. 处理 Pipeline（顺序铁律，错了=毁容）

```
解码(支持JPG/TIFF/中画幅) → 智能降噪(双边滤波) → 降采样到目标长边 →
频域视觉掩蔽(不可见高频让位主体) → 内容自适应锐化(显著性Mask加权) →
感知量化表编码(填满阈值预算的JPG, mozjpeg可选)
```

**顺序不可调换的理由**：
- 先降噪再降采样：噪点在高频，降采样会把噪点糊成块；先降噪则采样干净。
- 先降采样再锐化：锐化在目标分辨率上做，否则大图锐化再缩小=白做且放大块效应。
- 锐化必须在编码前最后一步：编码会柔化，输出锐化补偿平台二压的软化（Instagram 实测建议）。

**中画幅/1亿像素输入**：必须先降采样到目标长边再进感知评估，否则感知图（saliency/CSF）内存爆炸、速度崩。

## 4. 三大技术抓手（实现要点）

### 抓手 1：预处理感知增强（低风险，先上）
- **智能降噪**：双边滤波（Bilateral Filter）或 imageproc 实现，纯 Rust 零大依赖。抹平高 ISO 暗部噪点 → 同等视觉质量下体积降 15–30%（JPEG 把噪点当细节保留是码率杀手）。
  - 默认 `denoise_strength=25`（非 30，>40 出塑料脸）。
  - **二次压缩 JPG 禁降噪**（放大块效应）；RAW/TIFF 解码后参数与 JPG 分开。
- **频域视觉掩蔽**：用 CSF（对比敏感度函数）+ 纹理掩蔽，把人眼不可见的高频系数位让给主体区域（量化时主体少砍、背景多砍）。
- **内容自适应锐化**：频谱残差显著性检测（Saliency，纯算法）生成「主体亮、背景暗」灰度 Mask，加权 USM 锐化（主体 100%、平滑背景 0%）。Mask 边缘必须高斯模糊平滑，否则锯齿锐化边界。

### 抓手 2：轻量感知量化表（核心，Guetzli-lite，接受慢）
- 不跑完整 Butteraugli（太慢），用 **CSF 对比敏感度 + 纹理掩蔽** 快速评估每块「视觉重要性」。
- 在**阈值预算（体积安全线）内二分/迭代搜索每块最优量化强度**：预算内把质量顶满，超预算则按视觉重要性优先保主体。
- **星大明确：就算现在慢点也值** → 单张目标 ≤3s（20 张内批量总耗时可控），不做激进超时砍质量。
- 输出仍是 100% 标准 JPG（微信 100% 识别、不二压）。

### 抓手 3：mozjpeg 编码器（可选 feature，默认关）
- 同画质下体积比标准 libjpeg 再小 20–30%（Mozilla 维护多年、多产品验证）。
- `--features mozjpeg` 编译；Windows 用 MSVC 原生构建（比 cargo xwin 交叉编 C 库容易）。
- 默认关闭保零依赖；Mac 自用版可开。

## 9.1 评审答疑：相对 v4.1.0 WeChat(900KB) 档的真实增益，与"确保看得见提升、不白折腾"的保障

### A. 现状事实（已读代码确认）
- `ProcessMode::WeChat` 现状：`max_dim=2048, quality=95, target_kb=900`。
- 编码路径 `process_normal`：降采样 → 可选锐化 → `jpeg_encoder::Encoder::new(buf, quality)` **标准量化表**。
- **无任何感知优化**：视觉掩蔽、显著性、CSF 对比敏感度均未使用；标准量化表对每块用均匀量化强度，码率均匀分配。
- `use_custom_quantization` 字段已在 `ProcessConfig`/`AppConfig` 声明（默认 false），但 `process_normal` 未引用 → **悬空，本分支直接落地它**，不新增字段名。
- 现有 `smart_adaptive_sharpen()`（lib.rs:804）可复用为显著性锐化基础。

### B. 增益来源分解（为什么不是微小提升）
1. **同样 900KB 预算内，有效画质更高（核心增益）**：现在 900KB 里有一部分码率被标准量化表均匀浪费在"人眼看不出、但被当细节保留"的高频纹理/噪点上。感知量化表（Guetzli-lite）把这部分预算**重分配给主体边缘、色彩过渡、人脸**。结果：文件仍是 900KB（平台照样不二压），但你看到的清晰度/色彩明显更好。这是"画质保留更多"的准确含义——不是更小，是**同样体积里有效画质更高**。
2. **同画质体积更小（副产品）**：感知量化 + mozjpeg 可再 -20~30%，即 900KB 档可压到 ~650KB 还保持现观感。但主收益是第 1 点（填满预算堆画质）。
3. **降噪 + 显著性锐化额外增益**：暗部噪点抹平（画面干净 + 省码率），主体额外锐化（视觉清晰）。叠加在感知量化上，主观提升更明显。

### C. 诚实的量化预期（基于 Guetzli/感知量化已验证数据）
- 同体积主观画质：SSIM +0.01~0.03（对应肉眼可见"更清楚"），盲测 5 人中 ≥4 人偏好新图。
- 同画质体积：-20~30%（感知量化 + mozjpeg 叠加）。
- 边界说明：若现 900KB 档已 Q95 起点，增益主要来自"把浪费码率挪到主体"，不是从糊变清，而是从"均匀平庸"变"主体突出、背景干净"。仍是可见提升，但别预期"革命性"。

### D. 确保"看得见提升、不白折腾"的三板斧（验收铁律，写入代码）
1. **盲测门槛（主指标）**：同体积下 5 人盲测 ≥4 人偏好新图。仅 SSIM +0.005 之类微增**不算过**（那确实看不出）。
2. **A/B 对照生成**：同一图，旧路径(v4.1.0 WeChat 档) 与 新路径(感知量化) 都输出，放一起放大 200% 看睫毛/暗部。新增 `--ab` 模式一键产出对照图。
3. **benchmark 模式**：`--benchmark` 输出对比表（体积 / SSIM / PSNR / 各步耗时），星大可直接拍图发小红书。
4. **成功线（保画质优先，不激进）**：同体积 SSIM 不降 + 主观盲测胜（5人≥4人偏好）即算过；体积不强制降。"更清楚"是主指标，"更小"是副产品。达不到盲测门槛则本分支不 merge，维持 v4.1.0。

### E. 接口与复用决策（回应评审疑问）
- **GUI**：锁死不动。新功能先只开放 CLI/AI，GUI 用户保持 v4.1.0 原样；未来验证有效再单独讨论 GUI 是否加"平台预设"下拉（不替换现有档）。
